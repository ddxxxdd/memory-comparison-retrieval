# v6 全量实验：proposed vs bm25 / dense / hybrid

- 数据：`data/validmem_v6`（188 条写入、288 个冲突对、1225 条旧记忆，正文含用户名）
- 索引：`runs/indexes/validmem-p11-v6`（protocol 8 / prompt 1.7）
- 运行：`runs/experiments/v6-20261029b`，6 并发，188 条全量
- 评估：候选集合与 gold 直接比对；未启用逐对判定器

## 一、主结果（四种方法都经过同一套主体裁决）

| 方法 | 候选召回 | 纯度 | 候选/查询 | 个人渠道 | 公共渠道 |
|---|---:|---:|---:|---:|---:|
| **proposed** | **0.9618** | **0.5795** | **2.54** | 197/202 = 0.975 | **80/86 = 0.930** |
| dense | 0.9167 | 0.3188 | 4.40 | 202/202 = 1.000 | 62/86 = 0.721 |
| bm25 | 0.8924 | 0.3197 | 4.28 | 202/202 = 1.000 | 55/86 = 0.640 |
| hybrid | 0.9097 | 0.3251 | 4.29 | 202/202 = 1.000 | 60/86 = 0.698 |

proposed 召回最高、纯度约为三条 baseline 的 1.8 倍、候选数只有一半。
但**个人渠道三条 baseline 都是 1.000，proposed 0.975**——这一列不构成优势，见第三节。

## 二、普通方法不足之一：候选里八成是别人

取未经过滤的粗候选前 10 条，模拟"普通 top-k，不做主体判断"：

| 方法 | personal 渠道 | 前 10 条里属于其他用户的个人记忆 | 占比 |
|---|---|---:|---:|
| dense | 166 条查询 | 1353 / 1660 | **81.5%** |
| hybrid | 166 条查询 | 1363 / 1660 | **82.1%** |
| bm25 | 166 条查询 | 1346 / 1660 | **81.1%** |
| proposed（仅粗筛） | 166 条查询 | 1162 / 1456 | 79.8% |

实例（dense，查询 `Uma Evans's preferred grocery store is Whole Foods`）：

```
TC-A-0006  Uma Evans's preferred grocery store is Walmart       ← 目标
TC-A-0006  Uma Evans's preferred grocery store is Trader Joe's  ← 目标
TC-A-0005  Tina Evans's preferred grocery store is Walmart.     ← 别人
TC-A-0002  Quinn Evans's preferred grocery store set to Walmart ← 别人
TC-A-0029  Mia Fisher's preferred grocery store is Whole Foods  ← 别人
TC-A-0060  Liam Chen's preferred grocery store is Walmart       ← 别人
```

这条查询的粗候选里另有 **48 条**其他用户记忆被主体裁决过滤掉。也就是说：**相似度检索本身找得到目标，但会把目标埋在 4–5 倍于此的"别人同类记忆"里**，下游逐对判定要为此多付约 5 倍预算。

## 三、普通方法不足之二：过滤之后世界渠道掉三成

主体裁决能让候选变干净（个人渠道混入降到 0–2 条），但过滤不产生新的检索能力：

- 公共渠道（86 个冲突对）：proposed 0.930，hybrid 0.698、dense 0.721、bm25 0.640。**普通方法漏掉约 1/4–1/3 的公共冲突**。
- 个人渠道三条 baseline 满分是**结构造成的假象**：主体过滤后每个 query 只剩 1–2 条同用户记忆，top-k 必然全覆盖（它们的最终候选 3.5–3.7 条，其中包含不同的同用户记忆）。proposed 在此反而丢 5 对。

结论：普通方法在个人渠道靠"合法池极小"取胜，在公共渠道明显不足；proposed 是唯一在两个渠道都稳定、且候选数最少的臂。

## 五、边界

- **168 条 `Patient/患者` 记录仍是"角色"主体**：数据集生成脚本后续加了规则，认为"患者"是正文事实主体、不能等同于记录用户，所以没有写人名。这些记录的主体判为 unknown → 保留候选，个人渠道因此仍有一批无法区分主体的记录。
- 个人渠道难度不足是结构性的（同用户旧记忆平均 1.2 条），加人名只解决"能否看出是谁"。
- 金标仍未做全库逐对人工复核。
- 写延迟受 API 缓存影响（大量命中缓存），不能当作实测时延。
- 本轮为保证实验跑通做了两处解析容忍：`subject_relation` 缺省按 uncertain；假设句超预算时截断而非整条失败。71 项测试通过。
