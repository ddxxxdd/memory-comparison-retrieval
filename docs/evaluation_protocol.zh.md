# 检索评测口径与结果解读

本文对应当前主包的 [evaluation.py](../memory_retrieval/evaluation.py)、[sparsecl.py](../memory_retrieval/sparsecl.py) 和 STALE 60 场景实验入口。它定义当前指标及限制；具体数值放在 `reports/`。

## 1. 评测对象与候选范围

每条新记忆只检索自己的场景旧库。用 $G_q$ 表示查询 $q$ 的已标注目标集合，$L_q$ 表示方法返回的有序候选，$H_q(K)=|G_q\cap L_q[:K]|$。`conflict_old_memory_ids` 同时包含应检索的事实冲突和状态失效，当前总体指标不区分两者。

主方法、两项消融、BM25、Dense 和 Hybrid 对场景内完整旧库排序。SparseCL 先用冻结 BGE 的 HNSW 最多取 1,000 条，再按 cosine + alpha × Hoyer 排序；未进入初召回的目标记为未命中，不从分母删去。当前 STALE V2 场景库最多 333 条，因此该设置覆盖全部场景候选。不同规模的其他数据集不能自动作此假设。

## 2. 已实现的指标

| 字段 | 定义或用途 |
| --- | --- |
| `hits / gold_pairs` | 所有查询的命中目标数 / 所有已标注目标数 |
| `micro_recall` | $\sum_q H_q(K)/\sum_q \lvert G_q\rvert$；当前报告 Top-3/5/10 括号里的百分比 |
| `macro_recall` | 各有目标查询的 $H_q(K)/\lvert G_q\rvert$ 的算术平均；与 micro 不同 |
| `fully_covered_queries` | 前 K 名覆盖全部已标注目标的查询数；不是“语义上所有冲突已找全”的证明 |
| `recall_by_source` | 分别统计 `stale_native`、`synthetic_review` 等来源的目标数与命中数 |
| `gold_ranks` | 每个已标注目标的 1 起始名次；候选池没有返回时为 `null` |
| `labeled_hit_fraction` | $\sum_q H_q(K)/\sum_q\min(K,\lvert L_q\rvert)$，即已标注命中占返回候选的比例 |
| `candidate_purity` | 发现 `fully_reviewed=false`、待定或不确定标记时输出 `null`；不能把其他数据缺少这些字段当作已经完成语义审核的证明 |

NDCG@10 使用二值相关性：在 $G_q$ 内为 1，其余为 0；按 $1/\log_2(r+1)$ 折损，理想排名前 $\min(10,|G_q|)$ 位均为目标，再按查询取算术平均。目标为空的查询 NDCG 记 0；macro recall 跳过此类查询。STALE 当前每场景都有目标，不支持从这些结果推断无冲突写入的误报率。

程序不会在计算 NDCG 时排除待定项或把它们从排名中抽掉；它们和其他未列为目标的记录一样不获得相关性分数。这是相对于已知目标的评测约定，不是把待定项判定为真实相容。

## 3. 纯度与核查成本的边界

真正的 Precision@K 需要知道候选中哪些是冲突、哪些相容。V2 的新增历史没有逐条语义标注，旧待定列表也不完整覆盖全部未审历史，所以目前只能报告已标注命中比例，不能据此宣称真实候选纯度。

固定 K 还受到目标数量上限影响：只有 3 个目标时，理想排序的 Precision@10 也最多 30%。这不使 Precision 无效，但不能单独用它衡量不同场景的排序水平。NDCG 已反映目标的前后位置；它不能直接说明要检查多少条才能找全。

以下属于后续评测设计，**尚未成为当前统一入口的输出指标**：MAP、达到指定召回率所需候选数、同召回下多检查的非目标数、经独立标注确认的候选纯度、可变候选量及无冲突场景的停止质量。只有金标覆盖足够时才能将“非目标”解释为“真实干扰项”。用真实金标数计算的截止点只用于离线评测，不能成为线上停止规则的输入。

## 4. 对照与消融

六个现有检索基线为 BM25、BGE Dense、Hybrid、SparseCL ArguAna/MS MARCO/HotpotQA；冻结权重、编码长度及融合参数见 [model_lock.json](../memory_retrieval/model_lock.json)。基线不读取 gold 参与排序；来源字段不作为正文编码。模型已有预训练或检查点训练不等于本项目在 STALE 上训练。

三个方法臂在同次实验中共享相同探针、编码器和向量；扩散臂使用同一场景图。`仅正扩散` 指“探针初分 + 正源扩散”，不是去掉探针。完整方法比正扩散多的是自身与邻域的负向惩罚。相邻消融的差值说明该设置中的增量，不是三个模块在所有组合下可加的独立因果贡献。

主包 CLI 默认运行主方法；`--arms all` 加入六个基线，但不自动包含两项消融。九臂对照须写 `--arms all anchored_probes_only anchored_pos_diffusion`。单次 LLM 重排和 Qwen 编码器替换使用独立实验入口；它们不在 `all` 中。

60 场景脚本另提供逐查询 NDCG 的配对 Wilcoxon 和按 T1/T2 分层的 20,000 次 Bootstrap。报告的总体主要显著性对照是完整方法对 Dense、SparseCL MS MARCO；没有为某个模块给出配对检验，就不能把正的平均差值直接写成统计显著。p 值未做多重比较校正，分组分析按探索性结果解读。

## 5. 如何识别数据版本和复现结果

截至 2026-11-23，最新完成的 STALE 比较为 [V2 60 场景九臂报告](../reports/stale_v2_60scene_bipolar_seed20261122_experiment.md)：16,188 条旧记忆、333 个目标。旧 [V1 60 场景报告](../reports/stale_unseen_60scene_bipolar_seed20261122_experiment.md) 为 6,673 条旧记忆、340 个目标。全量 V2 构建的 400 场景/2,218 目标不是本次实验的分母。

V2 沿用 V1 的 60 个场景及查询，删除其中 7 个历史目标标签；同口径比较须用 V2 的 333 个目标重新计算 V1 排名。V2 还重新生成了探针，因而跨版本差值同时受到候选库和探针变化影响；不能归因于单一因素，也不能称作独立新 Test。已有 V1 的 Qwen、重排、原生单目标实验不能直接移作 V2 对照。

固定 60 场景入口输出 `comparison.json`，主包通用 CLI 输出 `report.json`；两者均保留 `arms/` 中的实际排名。`completion.json`、独立核验文件和输入哈希用于确认完成状态及结果身份。汇总状态中的编码进度子字段可能保留旧状态，是否完成应同时查看最终产物和核验。

历史实验目录保留当时的提示词、参数、查询顺序、输入、排名和缓存。读取实验时核对版本及目标数，不根据目录中的 seed 推断执行日期。提示词、数据或方法发生变化时使用新的输出目录，避免混写已有结果。基于已经查看的测试结果修改方案后，这些场景只能作为已见复测；泛化论证还需独立留出数据及冻结后的协议。

LLM 请求次数、成功响应 Token、重试、编码时间、评分时间和批次墙钟时间应分别报告。并行阶段不能相加当总时间，也不能把九方法批次总时间当作主方法单臂时间。主方法只读新记忆，LLM 重排还读候选；相同调用次数不等于相同 Token 预算。当前没有完成端到端下游核查及生产环境增量更新评测。
